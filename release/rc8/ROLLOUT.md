# Rollout plan — execution requires separate authorization

No step in this document has been executed against a live pilot or production service. RC.8 preparation creates no tag/release, publishes no registry/container/site artifact, sends no invitations and performs no deployment. Use the final kit manifest and evidence, not a floating branch or `latest` image, for the review decision.

## Review and preflight

1. Approve the consolidated CMS diff and the unchanged CLI #67/MCP #30 inputs after reviewing their exact revisions, dependency locks, safety regressions and this recovery plan. Keep all historical drafts as provenance; avoid duplicate merges. Obtain explicit merge, publication and deployment authorization before each corresponding live action.
2. Inventory any external embeds and cross-origin marketplace/starter previews on a prospective host: RC.8 intentionally blocks them by default. Such uses require an approved tested exception before upgrading that host. Select the pilot host, owner/support contact, ten private recipient-to-site assignments, resource limits, monitoring and maintenance window. Synthetic test staging is not implicitly promoted into a real-client host. Builders get per-site developer roles; clients get per-site editor roles; neither gets server-wide developer access. Confirm production validation/limiter are enabled and development auth is disabled.
3. Supply dedicated SMTP sending credentials and a verified sender through the private local worksheet. After separate authorization, configure only the selected disposable mail-test target and send an invitation/reset to the controlled test recipient. Verify inbox delivery, exact HTTPS host/path, account scope, setup/login/reset and authenticated encrypted transport. Capture-only SMTP evidence is insufficient. A successful role create is not proof of delivery: monitor invitation errors and have an operator recovery/resend procedure.
4. Check the host's ingress identity model. The RC.7 Railway fixture trusted only its edge-written `X-Real-IP`; do not copy that trust setting to a different/publicly bypassable ingress. Verify realtime registration and actual cross-tab events while preserving the limiter. Confirm backup storage is private, has usable space and retention, and excludes externally exposed download paths.
5. Capture a consistent pre-change backup of database, uploaded/compiled files and protected settings. Record source binary/image/version, backup checksum, owner and expected site/content/role/file inventory. Rehearse restoration into a separate empty target before accepting the backup as usable. The automated rehearsal uses generated data; any real-site restore needs a separately approved sanitized copy. Review mail/storage secrets before exporting backups.

## Package and publication order, after authorization

1. Release the approved MCP first. The tested candidate is 0.1.11-rc.2; a stable version choice or changed registry reference is a new artifact identity, not a rename of the tested bytes.
2. Resolve that exact approved MCP registry package in CLI and CMS test dependencies, replacing the temporary local tarball resolution and refreshing integrity locks. Repack CLI and rebuild CMS with the approved versions. Install into a fresh disposable home/workspace; rerun byte verification, CLI tests, compiler cases, native production tests and the packaged client handoff. Any source/version/lock/reference/bytes change invalidates the previous artifact approval.
3. Make the approved compatible CMS available before the public CLI, using only the selected verified executable or image digest. Publish the CLI last, then verify a fresh registry installation and handoff. Never rely on `latest` to identify the approved CMS.
4. **CMS repository coupling matters:** pushing `main`, `feature/**` or `rc/**` can publish a container; matching v3 release publication, including a prerelease, can publish images/update `latest`; tags trigger binary-release automation. Inventory and control consumers/autorollout before any approved merge, tag or release. Do not publish a prerelease as a supposedly harmless test. The preparation branch is `release/founding-builders-rc.8`, which does not match the container push branch patterns.

## Controlled pilot activation

After deployment authorization, start the approved CMS with its own restored/copied data, verify health/version/artifact identity and configuration, then check sign-in, scope denials, source/content round trip, nested reorder, editor/publication behavior, cache revalidation, same-origin previews and cross-origin framing refusal. Keep the prior verified deployment/backup available during the window. Do not apply an old executable to an upgraded database for rollback.

After explicit recipient-specific invitation authorization and verified real email, onboard one builder first, then the remaining nine. Each receives the [builder checklist](../../tests/staging/pilot/BUILDER-GUIDE.md). Record receipt, successful setup/reset, correct site role and a disposable local/remote conflict exercise. Use draft/preview work initially; no real client publication occurs under the current no-publish instruction.

Account and role provisioning is operator-assisted: the existing user/account and assignment creation rules require the server operator. A site-scoped developer can build and edit its assigned site's design/content, but cannot create a new client account or grant that account access. The operator must create and invite the requested client with the editor role. The disposable exact-package probe verifies rejection leaves no account behind and operator provisioning/client login succeeds. Delegated invitations would be a separate product/security capability outside the frozen pilot scope; do not grant shared-server developer authority as a workaround.

Before each builder's first client launch, clear physical iPhone Safari/Android Chrome public-page checks, the actual custom-domain/HTTPS/CDN path if used, the accepted framing policy and the complete content-only client handoff plus backup/support ownership on that host. Legacy imports require their representative fixture gate. Resolve these gates while builders create drafts, rather than adding unrelated requirements to invitation readiness.

## Pause and abort criteria

Pause the affected workflow for any silent content loss, cross-site access, destructive stale-conflict resolution, broken password recovery, unusable restore, persistent server failures or failure to serve the prior live publication after a failed publish. Freeze publication/editing as necessary to preserve data and use [RECOVERY.md](RECOVERY.md). The accepted one-hour performance limits cover the tested API/content workload; they do not promise visual page-load time, ten simultaneous browser compilations or a production uptime SLA.
