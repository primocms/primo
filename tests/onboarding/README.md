# Agent-assisted local onboarding

`Develop locally` supplies a server-specific prompt and an explicit files/CMS authoring choice. A command-capable local agent performs installation and development commands; the person chooses a folder, approves software/file access, and grants browser consent. It is not an agent installer or a GUI process manager.

## Release gates

- `tests/platform/fresh-machine.test.mjs` runs on Linux x64/arm64, macOS x64/arm64, and Windows x64 in `rc-platform.yml`. Each test starts with an empty HOME, package cache, install prefix and PATH: neither Node nor Primo is initially available. The host test process stands in for the already installed coding agent. It installs a private Node 22.17.0 runtime with verified distribution provenance and an executable matched to the official bytes (see delivery below), then installs the exact coordinated CLI/MCP archives with lifecycle scripts enabled. This tests a supported minimum runtime, not whichever Node happens to be installed on a runner.
- The native scenario initializes a workspace, preserves an existing agent tool while wiring the selected project MCP, and makes actual protocol calls through absolute launch paths without inheriting the installation PATH. It checks the normal managed CMS download plus an exact tagged executable for prereleases outside latest stable, file imports, duplicate-server refusal, an occupied port and safe retry, agent reconnection, mode switching/writeback, rendered preview, production build, logs and owned-process shutdown.
- `tests/onboarding/browser.test.mjs` repeats installation in each of Chromium, Firefox and WebKit. A disposable production-mode CMS creates synthetic users and two sites; the onboarding profile has no saved auth and receives no injected token. Actual browser password sign-in and device approval drive the installed CLI. Decline saves no credential; a new approved request resumes it. The test pulls only authorized sites, starts the imported local workspace, opens its real editor and preview, reconnects MCP, and verifies the hosted source has not changed.
  WebKit selects visual authoring from a fresh workspace: the agent driver seeds in files mode before switching, edits actual browser content and verifies local writeback. This prevents mirroring an initially empty local CMS over a copied shared library.
- `tests/e2e/mobile-layout.spec.ts` checks the real dashboard dialog at a narrow viewport, exact copied prompt, mode selection and blocked-clipboard recovery.

The candidates are unpublished. A loopback fixture redirects only the expected public GitHub managed/tagged release requests to the **actual frozen native executable**; normal CLI download, executable permissions and installed-version checks still run. It does not fake installation, the CMS, authentication, CLI commands, MCP responses, synchronization or rendering. Evidence records this delivery substitution and binary/package hashes. Public onboarding remains unavailable until coordinated packages and the CMS release are published. The prompt explicitly stops on unavailable or mismatched releases.

These are fresh-profile execution tests on supported CI OS images. They do not claim a pristine OS image, validate every third-party agent's installation/UI, or automate OS permission approval. Generated evidence is `fresh-machine-result.json` and `onboarding-<browser>.json`; the native workflow retains it alongside tested artifact provenance. No user credentials, real hosted content, or outgoing mail are used.

## Runtime distribution delivery

Native CI stages GitHub's maintained `actions/node-versions` distributions, the same mirror used by `actions/setup-node`, with archive hashes pinned in `node-mirrors.json`. All five executable hashes were independently verified byte for byte against Node's official 22.17.0 archives after checking the official SHASUMS256 manifest; original archive hashes and their official checksum URL are retained in that file. The staging job verifies the mirror archive hashes and records the candidate source. Each native profile rechecks that provenance, unpacks a new private runtime, checks its executable against the official hash, and verifies its version before installation. Bundled setup scripts are not run.

This is distribution staging, not reuse of an installed runner runtime or a user's package cache. Hosted CDN transfers for the Mac archives were roughly 6 KB/s and exhausted the two-minute budget using both Node fetch and system curl, including Linux staging of the original archives. The pinned maintained mirror preserves runtime identity and all installation/product assertions. The three Linux browser scenarios and local runs also exercise direct official HTTPS acquisition. These remain fresh-profile tests on supported OS images, not a claim about pristine OS installers or every third-party agent UI.
